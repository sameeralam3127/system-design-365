Designing Twitter

A read-heavy social feed at planetary scale: how tweets are written once, fanned out to millions of home timelines, and served back in under 200 ms — with the fan-out hybrid, sharding scheme, and caching layers that make it work.

01Requirements & scope

Pin the problem before drawing boxes. Interviews reward a crisp scope statement more than an exhaustive feature list.

✅ Functional — in scope

  • Post a tweet (280 chars, optional image/video)
  • Follow / unfollow users
  • Home timeline — tweets from people you follow, reverse-chronological (ranking noted as an extension)
  • User timeline — one user's own tweets
  • Like, retweet, reply (counts on each tweet)
  • Search tweets; trending topics

🚫 Out of scope

  • DMs, Spaces, communities, ads serving
  • ML ranking model internals (we design the hook, not the model)
  • Moderation / spam pipelines
  • Analytics & experimentation platform

The one-sentence framing: Twitter is a write-once, read-many system with extreme fan-out skew. Everything below is a consequence of optimizing the read path and taming the celebrity problem.

03API design

REST over HTTPS at the edge; services speak gRPC internally. Cursor pagination everywhere — offsets don't survive a moving feed.

  • Auth: OAuth 2.0 bearer tokens, validated at the API gateway; user ID flows to services in signed headers.
  • Rate limits: per-user token buckets at the gateway (e.g. 300 tweets / 3 h, 900 timeline reads / 15 min) — protects fan-out from abuse.
  • Media: client requests a presigned URL, uploads directly to object storage, then attaches the returned media_id — tweet write path never carries bytes.

05The write path: hybrid fan-out

The defining problem. Push (fan-out-on-write) gives cheap reads but explodes for celebrities; pull (fan-out-on-read) gives cheap writes but makes every read expensive. Twitter does both.

Push — fan-out on write

  • On tweet: insert its ID into every follower's cached timeline
  • Read = one Redis list fetch → fast, O(1)
  • Cost: 100 M followers × 1 tweet = 100 M writes 💥
  • Used for: the ~99.9 % of users with normal follower counts

Pull — fan-out on read

  • On tweet: write once to the author's own list, nothing else
  • Read = fetch tweets of everyone you follow, merge — O(following)
  • Cost shifts to every single timeline load
  • Used for: celebrity accounts (> ~1 M followers) and cold/inactive readers
  • Latency budget: median fan-out completes in < 5 s; a Lady Gaga-scale push would take minutes and melt Redis — hence the celebrity bypass.
  • Active-only optimization: fan out only to followers active in the last ~30 days. An inactive user's timeline is rebuilt via pull when they return — this cuts fan-out volume by 50 %+.
  • Ordering: partition Kafka by author ID so one author's tweets are processed in order; readers see global order via time-sortable Snowflake IDs, not delivery order.
  • Unfollow / delete: lazy repair — filtered out at read time (hydration checks tweet existence and block/unfollow sets) rather than eagerly scrubbing millions of lists.

06The read path: serving a home timeline

1.2 M requests/s at peak, p99 under 200 ms. The invariant: the hot path touches only memory.

  • Why store IDs, not full tweets, in timelines? 20 bytes vs ~1 KB per entry (50× less RAM), edits/deletes stay consistent (one canonical copy), and hydration hits a shared hot-tweet cache with a very high hit rate.
  • Cold user (cache miss on the whole list): rebuild via pull — fetch following, grab each one's recent tweet IDs, merge, cache the result. One slow load (~1–2 s), fast thereafter.
  • Graceful degradation: if the celebrity-merge or ranking step fails, serve the raw precomputed list — a slightly stale, unranked timeline beats an error.

07Data model & storage choices

Snowflake IDs — 64 bits, time-sortable, coordination-free

Every tweet needs a unique ID minted at 17 k/s across many hosts. Auto-increment can't be sharded; UUIDs aren't sortable. Snowflake packs time into the high bits so sorting by ID is sorting by time — which is what makes cursor pagination and timeline merging trivial.

08Deep dives

Search & trending

  • Ingestion: index workers consume tweet_created from Kafka; tweets are searchable within seconds. The index is time-partitioned — a query starts at the newest partition and walks backwards, terminating early once it has enough results.
  • Query: scatter-gather across shards of the relevant time partitions; blend recency + engagement for ranking.
  • Trending: a streaming job (Flink/Storm) runs sliding-window counts over hashtags/phrases with a heavy-hitters sketch (count-min), scores by acceleration vs a historical baseline (so "Monday" never trends), segments by geo, and publishes top-K to a cache every ~60 s.

Engagement counters at scale

  • A viral tweet takes thousands of likes/sec — a per-row DB counter becomes a hot spot. Instead: INCR sharded Redis counters (split hot keys into N sub-counters, sum on read), roll up to durable storage every few seconds.
  • Display counts are eventually consistent and approximate ("1.2 M") — nobody audits them; the likes table remains the source of truth for "did I like this," which must be exact.

Availability & multi-region

  • Stateless services scale horizontally behind LBs; Redis and DBs run replicated with automated failover.
  • Multi-region: active-active for reads (each region holds full timeline caches), writes homed to one region per shard with async cross-region replication — a few seconds of cross-region staleness is within the consistency budget.
  • Degradation ladder: drop ranking → serve stale cache → serve user-timeline-only. Never a blank feed.
  • Back-pressure: if fan-out lag grows, Kafka absorbs the backlog — tweet posting never blocks; timelines just go slightly stale, and lag is the #1 dashboard metric.

09Trade-offs & interview talking points

DecisionWe choseWe gave upWhy it's right here
Fan-out strategyHybrid push + pullSimplicity of a single pathPure push melts on celebrities; pure pull makes every read O(following). The split costs one branch and buys both cheap reads and bounded writes.
ConsistencyEventual (seconds)Read-your-follower's-write immediacyFeed staleness is invisible at 5 s; the RTT and coordination cost of strong consistency is not. Author always sees their own tweet instantly (write-through to own timeline).
Timeline storageIDs in Redis, capped at 800Infinite scroll of precomputed feed50× RAM savings, one canonical tweet copy; < 0.1 % of sessions scroll past 800 entries — those fall back to pull.
Delivery semanticsAt-least-once + idempotent insertExactly-once machineryA dedup check on LPUSH is cheap; distributed exactly-once is not. Missing a tweet is worse than a redundant retry.
CountersApproximate, sharded, async rollupExact real-time countsHot-key correctness at thousands of writes/sec would serialize on a row lock for a number nobody verifies.

Extension questions to expect

  • Ranked (ML) timeline? Keep the same candidate-generation machinery; insert a ranking service between hydration and response that scores ~500 candidates per request with engagement-prediction features.
  • Real-time delivery (new-tweets banner)? WebSocket/SSE gateway subscribed to fan-out events for online users — push the signal, let the client pull the tweets through the normal read path.
  • Edit/delete propagation? Nothing to fan out — timelines hold only IDs, so hydration reflects the canonical row immediately; just invalidate the tweet cache entry.
  • Thundering herd on a viral tweet? Request coalescing at the cache layer (single flight), plus per-object hot-key replication in Memcached.
